# Job-Sync 二开需求：国内技术岗智能筛选系统

## 1. 背景

国内技术岗职位描述噪音高，岗位来源分散，且“远程”“弹性”“Hybrid”“驻场”“线下办公”“外包”“培训”“薪资范围”“经验要求”等信息经常混在 JD 里。用户的目标不是海投，也不是自动批量开聊，而是先用一组可配置限制卡掉明显不合适的岗位，再借助 AI 根据简历判断个人匹配度、公司质量和投递价值，最后由人工确认后精准投递。

现有 Job-Sync 已具备 Boss 岗位采集、SQLite 职位库、AI 职位分析、简历优化和 PDF 导出能力。二开方向是在原有“岗位采集 -> AI 分析 -> 简历优化 -> PDF 导出”工作流上，强化为面向国内技术岗的可配置求职研究系统。远程是重要需求之一，但不是唯一主轴；它应作为筛选限制或偏好标签参与流程。

当前项目实际技术栈为 Tauri + Vue + Rust + Node sidecar，不是 Electron。二开目标用户当前主要在 Mac 上使用，因此后续主运行形态应保持 Tauri-first，但优先补齐 Mac 开发、运行和打包适配。Tauri 桌面端继续作为主路径，Docker 和纯 Web 服务暂不作为二开主线。

## 2. 产品目标

Job-Sync 二开后的核心流程是：

```text
找到真正适合的岗位
-> AI 分析匹配度
-> 人工确认
-> 精准投递
```

系统应成为“AI 求职研究员 + 岗位聚合器 + 可配置筛选器”，帮助用户每天从多个来源中筛出少量高价值岗位，并围绕每个岗位生成可解释的限制命中结果、技术匹配分析、公司风险判断和投递准备材料。

## 2.1 运行形态目标

二开后的首选运行方式应是 Mac 上的 Tauri 桌面端。现有 Vue 前端、Rust Tauri command、SQLite 本地存储和 Node sidecar 继续保留，优先解决 Mac 开发启动、Chrome 路径识别、sidecar 运行和 macOS 打包问题。

目标体验：

```text
git clone / 下载项目
-> 安装 Node + Rust 工具链
-> npm install
-> npm run tauri:dev
-> 完成采集、筛选、分析、审核和投递准备
```

推荐运行结构：

- Tauri Shell：提供桌面窗口、文件系统访问、本地命令调度和应用数据目录。
- Vue UI：复用现有前端页面和组件。
- Rust Commands：继续承接设置、SQLite、职位库、报告、简历、PDF 和 sidecar 控制。
- Node Sidecar：负责 Boss 采集、标签抽取、AI 分析和后续 worker 任务。
- SQLite：存储职位、简历、设置、分析结果和审核状态。
- Mac Chrome：作为 Puppeteer 采集和登录浏览器。

Mac 适配重点：

- 补齐 macOS Chrome 默认路径识别，例如 `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`。
- 确认开发模式 sidecar 能通过本机 `node` 启动。
- 增加 macOS 打包目标和说明，例如 `.app` / `.dmg`。
- 避免 release 配置只依赖 Windows `node.exe` 和 MSI。
- 保留人工登录 Boss 的浏览器流程，并持久化 Cookie / LocalStorage。

主要面向以下国内技术岗位方向：

- Go
- Infra
- DevOps
- SRE
- AI Agent
- AI Infra
- 云原生
- 平台工程

可配置偏好示例：

- 弹性远程
- Go / Infra / DevOps / SRE 相关
- 云原生或 AI Infra 相关
- 薪资、城市、经验、公司规模等满足个人预期

## 4. 目标用户

1. 正在寻找国内技术岗的 Go / Infra / DevOps / SRE / 云原生工程师。
2. 希望用自定义限制条件过滤岗位，再用简历匹配度排序的技术求职者。
3. 希望借助本地 AI 模型或 OpenAI Compatible API 做岗位研究，但不希望交出自动投递控制权的用户。

## 5. 产品边界

### 5.1 必须坚持

- Local-first：岗位数据、简历数据、分析结果优先保存在本地 SQLite。
- Human-in-the-loop：AI 只能推荐、分析、草拟，不能替用户自动投递。
- 精准求职：核心指标是每天发现、筛选和确认少量高质量岗位，而不是投递数量。
- 可解释决策：硬限制过滤、偏好评分、公司评分、简历匹配评分和最终排序都应能展示依据。
- 可回溯数据：每个岗位都应追踪来源平台、来源 URL、抓取时间、原始字段和去重 key。

### 5.2 明确不做

- 自动海投。
- 自动群发。
- 自动开聊大量招聘方。
- 自动刷 Boss 或绕过平台限制。
- 绕过招聘平台风控。
- 以投递数量为目标的增长功能。
- 替用户做最终投递决策。

## 6. 核心用户故事

1. 作为求职者，我希望从多个平台采集岗位，避免手动逐个平台搜索。
2. 作为 Go / Infra 工程师，我希望系统优先识别 Go、Kubernetes、Docker、AWS、Prometheus 和基础设施相关岗位。
3. 作为用户，我希望先配置硬限制条件，例如工作方式、薪资、城市、技术方向、公司类型和排除关键词。
4. 作为谨慎求职者，我希望不满足硬限制的岗位被直接过滤，而不是只靠低分排到后面。
5. 作为用户，我希望远程、Hybrid、到岗办公、驻场等工作方式只是筛选维度之一，可以按需要设为必选、排除或偏好。
6. 作为候选人，我希望每家公司都有 Company Score，帮助避开低质量雇主、中介和风险公司。
7. 作为技术候选人，我希望 Resume Match Score 能基于我的简历衡量技术栈、经验年限、项目经历和岗位方向匹配度。
8. 作为用户，我希望通过可配置权重排序，让最值得看的岗位排在前面。
9. 作为用户，我希望每天只审核 Top 20 候选岗位，而不是被大量低质量岗位淹没。
10. 作为用户，我希望维护公司、职位和关键词黑名单，让已知不合适的岗位从未来队列中消失。
11. 作为用户，我希望 AI 基于 JD、简历和技术交集生成定制化打招呼文案。
12. 作为用户，我希望系统生成每日岗位情报，展示新增岗位、高匹配岗位、满足关键限制的岗位和推荐投递岗位数量。
13. 作为本地模型用户，我希望支持 Ollama。
14. 作为 API 用户，我希望支持 DeepSeek 和 OpenAI Compatible API。
15. 作为隐私敏感用户，我希望保留现有简历优化和 PDF 导出流程，并保持本地优先。
16. 作为用户，我希望当前版本先只做好 Boss，但底层模型能为后续 Liepin、Zhilian、Maimai、V2EX、LinuxDo 留接口。
17. 作为用户，我希望筛选规则能覆盖薪资、是否远程、岗位发布时间、岗位方向、技术栈要求和我不会的技术。
18. 作为用户，我希望系统能读取或记录打招呼状态，避免重复处理已读未回、拒绝过或我手动标记不合适的公司和岗位。

## 7. 功能模块

### 7.1 职位来源与归一化

系统应引入统一来源模型 `job_sources`，逐步支持 Boss、Liepin、Zhilian、Maimai、V2EX 和 LinuxDo 等来源。首期只实现 Boss，不能因为预留多平台而拖慢当前闭环。

每个平台采集结果应先转换为统一内部职位模型，再进入标签抽取、硬限制过滤、AI 分析和排序流程。归一化模型应保留平台原始字段，并新增规范化字段，至少包括：

- 来源平台
- 来源 URL
- 抓取时间
- 去重 key
- 职位标题
- 公司名称
- 城市或地区
- 薪资范围
- 经验要求
- 学历要求
- JD 原文
- 原始平台 payload

首期应优先保持 Boss 现有采集链路可用，并让 Boss 数据迁移或映射到统一模型。

首期范围：

- 实现 Boss 来源的采集、归一化、去重、入库和后续筛选。
- 为其他平台保留 source adapter 接口和来源字段，但不实现其他平台采集。
- 排序、筛选画像、黑名单、沟通记录和简历匹配逻辑必须只依赖统一职位模型，不能和 Boss 平台字段强绑定。

### 7.2 筛选画像与硬限制规则

系统应支持用户维护一个或多个“岗位筛选画像”。筛选画像用于表达当前求职阶段的硬限制、排除条件和偏好条件，不能只靠一个总分解决所有判断。

筛选画像应至少支持三类规则：

- 必须满足：不满足就直接过滤，例如必须是 Go / Infra 相关岗位、必须满足最低薪资、必须支持远程或某城市。
- 必须排除：命中就直接过滤，例如驻场、外包、培训、销售、电话销售、明确线下办公。
- 偏好加权：不决定生死，但影响排序，例如长期远程加权、云原生加权、大厂背景加权、AI Infra 加权。

首批可配置维度：

- 工作方式：远程、长期远程、弹性远程、Hybrid、到岗办公、驻场、未知。
- 岗位方向：Go、Infra、DevOps、SRE、平台工程、AI Infra、AI Agent、云原生。
- 技术标签：Kubernetes、Docker、AWS、Prometheus、Linux、CI/CD、Terraform 等。
- 不会或不想做的技术栈：命中时可直接过滤或强降权，例如前端、Java、PHP、Windows 运维、销售型售前等。
- 薪资范围：最低薪资、最高薪资、是否接受面议。
- 岗位时间：发布时间、最后采集时间、是否只看最近 N 天新增岗位。
- 城市或地区：目标城市、可接受城市、不接受城市。
- 经验要求：年限区间、是否接受高于/低于当前经验。
- 学历要求：是否必须满足。
- 公司条件：公司规模、融资阶段、行业、是否外包或培训机构。
- 关键词：包含关键词、排除关键词、弱偏好关键词。
- 来源平台：Boss、Liepin、Zhilian、Maimai、V2EX、LinuxDo 等。
- 沟通状态：未打招呼、未读、已读未回、已回复、已拒绝、已标记不合适。

规则执行结果应记录解释信息，示例：

```json
{
  "eligible": false,
  "blocked_by": [
    {
      "rule_type": "must_not_keyword",
      "field": "job_description",
      "value": "驻场",
      "reason": "JD 明确出现驻场要求"
    }
  ],
  "matched_preferences": ["Go", "Kubernetes"],
  "missing_preferences": ["AI Infra"]
}
```

远程不再是固定主轴，而是工作方式维度中的一个可配置条件。用户可以把“远程”设为必须满足，也可以只把它设为偏好，甚至在某个筛选画像里完全不使用远程条件。

### 7.3 Company Score

Company Score 用于识别公司质量和风险，尤其是外包、培训机构、招聘中介、销售导向岗位和信息过少的公司。

结构化输出示例：

```json
{
  "company_score": 83,
  "risk_flags": ["outsourcing_risk"],
  "evidence": ["JD 中出现外包交付相关描述"],
  "confidence": 0.82
}
```

风险标签可包括：

- outsourcing_risk
- training_risk
- sales_like_risk
- low_info_risk

同一公司多岗位应尽量复用公司维度评分或缓存结果，避免重复分析。

### 7.4 Resume Match Score

Resume Match Score 用于根据用户简历、目标技术栈和目标方向评估岗位匹配度。它只负责回答“这个岗位和我是否匹配”，不负责处理硬限制。硬限制必须在进入排序前先执行。

目标技术栈首批包括：

- Go
- Kubernetes
- Docker
- AWS
- Prometheus
- Linux
- CI/CD
- Terraform
- 云原生相关工具链

目标方向首批包括：

- Infra
- DevOps
- SRE
- 平台工程
- AI Infra
- AI Agent
- 云原生

结构化输出示例：

```json
{
  "resume_match_score": 91,
  "matched_stack": ["Go", "Kubernetes", "Docker", "Prometheus"],
  "matched_direction": ["Infra", "SRE"],
  "matched_resume_evidence": ["简历项目中包含 Kubernetes 平台建设经历"],
  "experience_fit": "3-5年",
  "missing_points": ["AWS 经验未明确"],
  "confidence": 0.87
}
```

明显不相关岗位不能因为满足某个偏好标签而进入推荐前列。简历匹配应是排序中的强信号。

### 7.5 偏好评分、综合排序与 Top 20 审核队列

系统应在硬限制过滤后计算排序分，并默认展示 Top 20 候选岗位给用户人工审核。排序分不是过滤条件，不能让不满足硬限制的岗位靠高分“捞回来”。

默认排序可以采用可配置权重，而不是写死单一公式。首版建议默认权重：

```text
final_score = 0.6 * resume_match_score
            + 0.25 * preference_score
            + 0.15 * company_score
```

其中：

- `resume_match_score`：简历和岗位的匹配度。
- `preference_score`：岗位命中用户偏好标签的程度，远程、长期远程、云原生、AI Infra 等都可以在这里体现。
- `company_score`：公司质量和风险判断。

权重应允许用户在筛选画像中调整。系统默认偏向简历匹配，但不同求职阶段可以切换策略，例如“远程优先”“薪资优先”“技术成长优先”“稳定性优先”。

审核状态应至少包括：

- 待审核
- 已收藏
- 准备投递
- 已投递
- 忽略

系统可以推荐和解释，但不应提供自动批量投递入口。

### 7.6 黑名单与排除规则

Ranking 前必须先执行硬限制、黑名单和排除规则。黑名单是排除规则的一种，但不是全部；用户配置的必须排除条件也应进入同一条过滤链。

黑名单类型：

- 公司黑名单
- 职位黑名单
- 关键词黑名单

默认关键词：

- 外包
- 驻场
- 培训
- 销售
- 电话销售

过滤结果应记录原因，示例：

```json
{
  "filtered": true,
  "filter_type": "keyword_blacklist",
  "filter_value": "驻场"
}
```

筛选画像、排除规则或黑名单变更后，应支持重新计算过滤结果和推荐排序。

### 7.7 沟通记录与再筛选策略

系统应记录岗位或公司的打招呼状态，并让沟通状态参与后续筛选。沟通记录可以来自用户手动维护，也可以在后续能力允许时从平台页面读取。

沟通状态至少包括：

- 未打招呼
- 已打招呼未读
- 已读未回
- 已回复
- 已拒绝
- 手动标记不合适

记录字段至少包括：

- 公司名称
- 职位 ID 或去重 key
- 来源平台
- 上次打招呼时间
- 当前沟通状态
- 最后更新时间
- 用户备注
- 是否加入公司黑名单
- 是否加入职位黑名单

默认再筛选规则：

- 未打招呼：可以进入推荐队列。
- 已打招呼未读：可以重新进入推荐队列，但必须明显标记“未读”和上次打招呼时间。
- 已读未回：默认标记为不合适或低优先级，后续筛选可过滤。
- 已拒绝：默认不再进入推荐队列。
- 手动标记不合适：默认不再进入推荐队列。

用户应能在岗位审核队列中手动执行以下操作：

- 标记岗位不合适。
- 标记公司不合适。
- 加入公司黑名单。
- 加入职位黑名单。
- 修改沟通状态。
- 查看上次打招呼时间。

如果某公司出现已读未回、拒绝过或多次手动不合适，系统应允许把该公司加入公司黑名单，使后续同公司岗位默认被过滤。

### 7.8 定制化打招呼

系统应在用户人工确认岗位后，基于 JD、简历摘要、命中技术栈和岗位方向生成短、具体、可复制的打招呼文案。

要求：

- 文案必须引用岗位需求和候选人技术栈交集。
- 文案不能过度夸大或编造经历。
- 避免“您好，我对贵司岗位很感兴趣”这类泛化模板。
- 用户必须可以编辑后再使用。
- 系统不自动发送消息。

### 7.9 每日岗位情报

系统应能从本地职位数据生成每日岗位情报，至少包括：

- 今日新增岗位数量
- 高匹配岗位数量
- 满足关键限制岗位数量
- 推荐投递岗位数量

示例：

```text
今日新增岗位：38
高匹配：5 个
满足关键限制：8 个
推荐投递：4 个
```

通知渠道可以逐步实现。优先级建议为邮件，其次是企业微信或 Telegram。通知内容只包含摘要和入口，不自动投递。

### 7.10 模型供应商与本地化

系统应保留或增强以下模型接入：

- Ollama
- DeepSeek
- OpenAI Compatible API

要求：

- prompts、模型配置、温度和结构化输出 schema 应可配置。
- AI 结构化输出解析失败时必须有明确错误状态和重试入口。
- 不得把 API Key 写入项目代码。
- UI 不应明文展示已保存的 API Key。

## 8. 实施优先级

### Phase 0：源码基线与 Mac Tauri 适配确认

目标是在真正修改业务功能前，确认现有架构、可复现验证方式，以及 Mac 上 Tauri 开发、sidecar、Chrome 登录和打包适配边界。

任务：

- 确认 Tauri command、SQLite schema、岗位采集模块、AI 分析模块、简历优化模块和 PDF 导出模块。
- 确认 Mac 上 `npm run tauri:dev` 的工具链要求和启动路径。
- 补齐或验证 macOS Chrome 默认路径识别。
- 确认开发模式 sidecar 能通过本机 `node` 启动并收发事件。

### Phase 1：统一职位来源模型

目标是让 Boss 先跑通，同时保证 Boss 之外的平台以后可以逐步接入，而不是把每个平台写成独立孤岛。

验收：

- Boss 岗位仍能正常入库。
- 每条岗位都能追踪来源平台、来源 URL、抓取时间和去重 key。
- 当前只实现 Boss 来源，其他平台只做 adapter 接口和字段预留。
- 新平台 adapter 可以在不改 ranking 和 AI 分析模块的情况下接入。

### Phase 2：筛选画像与硬限制规则

目标是先建立可配置筛选画像，让系统能在打分前卡死明显不符合用户限制的岗位。

验收：

- 用户可以配置必须满足、必须排除和偏好加权规则。
- 工作方式、岗位方向、技术标签、不会或不想做的技术栈、薪资、岗位时间、城市、经验、学历、公司条件、关键词、来源平台和沟通状态可作为筛选维度。
- 不满足硬限制的岗位不会进入排序队列。
- 过滤结果能展示命中的规则和值。
- 远程可以被设为硬限制、偏好或完全不参与当前筛选画像。

### Phase 3：简历匹配与综合排序

目标是在硬限制过滤之后，根据简历匹配、偏好命中和公司质量形成每天可人工审核的精简候选列表。

验收：

- Resume Match Score 能解释岗位与简历的匹配依据。
- Preference Score 能解释命中的偏好标签。
- Top 20 排序符合当前筛选画像的权重配置。
- 用户可以确认、忽略或标记岗位。
- 系统不提供自动投递批处理入口。

### Phase 4：黑名单与沟通状态过滤

目标是把已知不想看的公司、职位、关键词、沟通状态和用户自定义排除条件稳定过滤。

验收：

- 黑名单和排除规则命中的岗位不会进入推荐列表。
- 已拒绝、手动标记不合适、默认过滤的已读未回记录不会进入推荐列表。
- 已打招呼未读的岗位可以重新进入推荐列表，但必须标记“未读”和上次打招呼时间。
- 用户能看到某岗位为何被过滤。
- 黑名单或筛选画像变更后可重新计算推荐结果。

### Phase 5：沟通记录管理

目标是把打招呼记录和人工判断沉淀为本地可复用的数据。

验收：

- 用户可以记录和修改沟通状态：未打招呼、已打招呼未读、已读未回、已回复、已拒绝、手动标记不合适。
- 用户可以查看上次打招呼时间。
- 用户可以把公司或岗位加入黑名单。
- 同一公司后续岗位能复用公司级不合适或黑名单判断。

### Phase 6：Company Score

目标是识别外包、培训机构和低质量公司风险。

验收：

- 能输出 `{ "company_score": 83 }` 形态的结构化结果。
- 外包、培训机构、电话销售等关键词能触发风险标签。
- 同一公司多岗位可复用公司评分。

### Phase 7：Top 20 审核队列

目标是把过滤和排序后的岗位收敛成可处理的人工审核工作台。

验收：

- 默认展示 Top 20 候选岗位。
- 每个岗位展示硬限制结果、简历匹配解释、偏好命中、公司风险、沟通状态和上次打招呼时间。
- 审核状态支持待审核、已收藏、准备投递、已投递和忽略。

### Phase 8：定制化打招呼

目标是让人工确认后的岗位进入高质量沟通，而不是套话群发。

验收：

- 文案明确引用岗位需求和候选人技术栈交集。
- 不生成泛化模板。
- 不自动发送消息。

### Phase 9：每日岗位情报

目标是每天给用户一份可行动的岗位摘要。

验收：

- 能生成新增、高匹配、满足关键限制和推荐投递统计。
- 至少支持一种通知渠道。
- 通知内容不触发自动投递。

### Phase 10：模型供应商与本地化增强

目标是让 AI 分析可以使用本地模型，也可以使用兼容 API。

验收：

- 用户可以选择本地 Ollama 或远程兼容 API。
- 结构化输出解析失败时有错误状态和重试入口。
- API Key 不写入项目代码，也不在 UI 明文展示。

## 9. 测试要求

- 硬限制过滤、偏好评分、Final Score 和黑名单过滤应优先作为纯逻辑单元测试。
- AI 解析应使用 fixture JD 文本做契约测试，验证结构化输出字段。
- 来源归一化应使用捕获或 mock 的平台 payload 测试。
- 审核流程必须测试不存在未确认的自动投递动作。
- 沟通状态过滤应使用固定记录测试未读、已读未回、已拒绝和手动不合适的处理差异。
- 黑名单测试应覆盖公司黑名单、职位黑名单、关键词黑名单和手动不合适沉淀后的过滤。
- 每日情报应使用固定职位数据验证新增、高匹配、满足关键限制和推荐投递统计。
- UI 测试应覆盖 Top 20 审核队列、评分展示、黑名单管理、沟通状态标记、上次打招呼时间和打招呼预览。

## 10. 总体验收标准

1. 多来源岗位可以存入统一的本地 SQLite-backed 模型。
2. Mac 用户可以通过 Tauri 桌面端完成核心流程。
3. 开发模式下 `npm run tauri:dev` 可以启动 Vue 前端、Rust Tauri Shell 和 Node sidecar。
4. 当前版本只实现 Boss 来源，但统一模型和 adapter 边界支持未来扩展其他平台。
5. 系统支持可配置筛选画像，包含必须满足、必须排除和偏好加权规则。
6. 筛选维度覆盖薪资、是否远程、岗位时间、岗位方向、技术栈、不想做或不会的技术、城市、经验、学历、公司条件、关键词、来源平台和沟通状态。
7. 不满足硬限制或命中排除规则的岗位不会进入推荐排序。
8. 每个进入排序的岗位都有 Resume Match Score、Preference Score、Company Score 和 Final Score。
9. Final Score 默认偏向简历匹配，且权重可随筛选画像调整。
10. 公司、职位、关键词黑名单和自定义排除规则命中的岗位不会进入推荐结果。
11. 已拒绝、手动不合适和默认过滤的已读未回记录不会进入推荐结果。
12. 已打招呼未读的岗位可以重新进入推荐结果，但必须显示未读状态和上次打招呼时间。
13. 用户可以手动标记公司或岗位不合适，并让该判断影响下次筛选。
14. 应用可以展示 Top 20 人工审核队列。
15. AI 可以生成定制化打招呼文案，但应用不能自动投递。
16. 系统可以从本地职位数据生成每日岗位情报。
17. Ollama、DeepSeek 和 OpenAI Compatible API 是一等模型选项。
18. 现有简历优化和 PDF 导出流程应被保留，并能和筛选后的岗位联动。
19. 产品文案和交互始终围绕“精准求职”和“岗位研究”，避免包装成自动投简历机器人。
