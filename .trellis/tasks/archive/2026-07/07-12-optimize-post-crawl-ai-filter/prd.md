# 优化采后岗位 AI 精准过滤

## Goal

让采后规则优先回答“这是不是一个真实招聘岗位、是否满足用户不可妥协条件”，再判断技术方向是否值得查看，减少因 AI/求职相关词命中或整体技术方向相似而产生的误推荐。

## Background

- 用户当前寻找 Go、Java、AI Agent 协作、AI 应用工程等相关岗位，并要求居家办公或远程工作。
- AI 应用/Agent 岗位允许使用 Python，但只接受 Python 服务于 LLM/Agent 应用、模型接入或 AI 工程化；纯 Python 后端、数据分析或算法研究岗位不属于目标方向。
- 用户明确不能接受要求英语交流、非远程、要求不会的开发语言/前端或全栈、明确要求全日制本科等岗位条件。
- 用户提供的误判样本一：渣打银行内推岗位虽然方向可能相关且支持居家办公，但正文明确要求英语交流，按用户规则必须过滤。
- 用户提供的误判样本二：“AI 模拟面试”是开源项目、产品介绍或求职工具推荐帖，不是招聘帖，不能因包含 AI、工作、简历、面试等词进入推荐岗位。

## Confirmed Facts

- 采后 AI 提示词由 `packages/boss-crawler-worker/src/ai/prompt.ts` 的 `buildPostCollectionJudgePrompts` 构造，输入包含完整 filter profile、系统采后理由、统一岗位字段、JD、原始 payload 和详情 JSON。
- 当前 system prompt 把所有“AI 软排除”描述为判断偏好；user prompt 仅要求命中时“应倾向 filtered”，没有区分不可妥协条件与普通负向偏好。
- 当前 prompt 没有先执行“真实招聘内容类型判定”，`recommended` 定义也偏宽，只要方向、职责、技术栈或公司信息“整体值得查看”即可。
- Rust `normalize_worker_bucket` 当前会把置信度低于 0.65 的任何 AI 结果改为 `pending_confirmation`，包括已经给出 `filtered` 的明确排除结果。
- V2EX 采集前分类仅通过招聘词计数判断：一个强信号，或两个弱信号即可入库；没有识别“模拟面试、求职工具、开源项目、经验分享、产品介绍”等非招聘意图。
- 本地真实记录 `v2ex:1225603` 当前被判为 `recommended`，AI 摘要为“明确的 AI 模拟面试产品，属于 AI 应用方向”，同时 risks 又承认它“更像个人项目/产品分享，未见明确招聘职责”；证明当前模型把“AI 应用相关”错误地放在“是否招聘帖”之前。
- 本地渣打银行样本正文明确包含“英文水平要求高，全英面试”和“英语工作环境”，现有 AI 结果却只把英语要求列为风险，没有按用户的排除规则直接过滤。
- 当前默认 profile 的不确定策略为 `filtered`，但 Rust 低置信度归一化仍会把所有低于 0.65 的结果改为 `pending_confirmation`，与用户可见配置冲突。
- 确定性黑名单、沟通状态和人工状态仍由现有 canonical filter profile 链路处理，AI 负责岗位内容相关判断。

## Requirements

### R1. 三个用户提示词形成清晰职责边界

- “我想看的岗位”描述正向目标、必须满足条件和加分项，不得覆盖排除条件。
- “AI 排除条件”描述有明确证据即过滤的不可妥协条件；证据不足的情况由“风险关注点”和不确定策略处理。
- “风险关注点”只描述信息不足、事实矛盾、需要核实的内容，不得把已经有明确排除证据的岗位降级成待确认或推荐。
- 默认文案和页面引导应让用户用可判定的自然语言填写规则，避免含糊的“倾向”“最好”“可能”等表达削弱过滤效果。
- 三个可见文本框是个人岗位偏好的唯一事实源。代码和隐藏 system prompt 不得硬编码英语、远程、学历、岗位方向、开发语言等个人筛选条件。
- 删除设置页旧有的“通用 AI 补充提示”和“结构化输出 Schema 补充”及其存储、环境变量和 prompt 注入链路，避免它们成为采后判断或其他 AI 功能的隐藏第二事实源；独立的“打招呼文案补充提示”继续保留。
- 修改三个文本框并保存、重算后，AI 必须按新文本生效，不要求用户修改代码或了解隐藏 prompt。

### R2. AI 按固定决策顺序判断

1. 先判断输入是否为真实、当前有效、面向候选人的招聘/内推岗位。
2. 再检查不可妥协条件；任一条件有明确正文证据时直接 `filtered`。
3. 只有通过前两层后，才判断方向、技术栈、职责和加分项是否匹配。
4. 只有事实缺失、语义歧义或条件冲突时才使用用户配置的不确定策略。
5. 正向匹配不得抵消明确排除；例如 Go/AI/远程匹配不能抵消“要求英语交流”。
6. 代码只提供与具体个人偏好无关的通用判断协议、优先级、证据约束和 JSON 输出格式；具体过滤内容必须从三个用户文本框读取。

### R3. 非招聘内容必须被识别

- 开源项目介绍、AI 模拟面试工具、课程/产品推广、求职经验、技术分享、招聘信息聚合说明等没有具体招聘主体、岗位需求或投递动作的内容不得进入推荐。
- 采集来源已有内容分类器时，应在入库前增加负向意图和组合证据判断，避免仅凭“招聘相关词”放行；明确非招聘内容直接跳过、不进入职位库，只保留采集日志和过滤事件供审计。
- AI 采后判断仍需保留通用内容类型门禁，以覆盖历史已入库数据及其他来源漏网内容。
- “必须是真实招聘/内推岗位”是职位库通用数据有效性规则，可以由代码保留；该规则必须在界面说明和结果原因中可见，不属于隐藏的个人偏好。

### R4. 明确排除结果不能被低置信度规则反向削弱

- AI 已输出 `filtered` 且提供可追溯排除证据时，不得仅因 confidence 低于统一阈值改成 `pending_confirmation`。
- 缺少证据、证据不可追溯或输出结构不稳定时，继续安全降级为 `pending_confirmation`。

### R5. 可解释与可回归

- AI 输出必须指出触发的规则、岗位原文证据和最终分桶原因。
- 解释必须区分规则来源，例如“命中【AI 排除条件】中的英语交流规则”，不得只给模型自己的概括性判断。
- 至少覆盖真实招聘但命中硬排除、非招聘 AI 工具帖、符合目标的真实招聘帖、信息不足帖子四类测试样本。
- 回归测试必须证明用户提供的两个样本不会进入 `recommended`。

## Acceptance Criteria

- [x] 明确写有英语沟通、英语工作语言、英文会议或同等要求的岗位，在用户配置“英语交流不行”时输出 `filtered`，即使同时命中 Go/Java/AI/远程等正向条件。
- [x] “AI 模拟面试”开源项目或产品介绍帖在没有真实岗位、招聘主体和投递信息时不会进入 `recommended`；新采集内容应尽量在来源分类阶段跳过，历史内容重算后应为 `filtered`。
- [x] 来源分类阶段跳过的明确非招聘内容不写入职位库，但继续产生可读的过滤日志或事件。
- [x] 正向目标、明确排除和风险关注三类提示词在 prompt 中有明确优先级，明确排除优先于正向匹配和风险策略。
- [x] 搜索代码中的 AI 判断模板，不存在英语、远程、学历、Go/Java/Python 等用户个人偏好的隐藏硬编码；这些条件只存在于可编辑 profile 文本或测试样本中。
- [x] 设置页、Rust 设置模型和 worker 环境中不再存在全局 prompt/schema 补充字段；采后判断只读取采集配置页的三段可见规则。
- [x] 用户修改任一文本框、保存并重算后，新规则实际进入 AI prompt 并改变后续判断。
- [x] `pending_confirmation` 只用于证据不足或矛盾场景，不用于已有清晰排除证据的岗位。
- [x] AI 判断证据能够追溯到岗位标题、JD、原始正文或结构化字段，不能只复述用户规则。
- [x] 现有黑名单、沟通状态、人工审核状态和公司状态硬规则语义保持不变。
- [x] 相关 worker 测试、Rust 测试、前端/合约测试与构建通过。

## Out of Scope

- 不改变用户的目标岗位方向或替用户放宽英语、学历、远程等个人约束。
- 不引入自动投递、自动沟通或简历决策。
- 不把所有招聘判断改造成纯关键词硬黑名单；仍保留 AI 对上下文和否定语义的判断能力。
