# 排查采集入库与 AI 解析计数不一致

## Goal

查明 2026-07-11 20:00 至 20:04 的 V2EX、LinuxDo 自动采集中，平台日志显示“入库 42/20 条”，但 AI 采后判断收到 0 个岗位的原因，并明确这些岗位的实际新增、更新和重复数量。

## Confirmed Facts

- V2EX worker 的“入库”日志使用 `captured` 计数，表示已发出标准化岗位事件，不代表数据库实际新增。
- LinuxDo worker 的“入库”日志同样使用 `captured` 计数。
- 页面只读取 `collection_run_job.outcome = 'inserted'` 的岗位 ID，并仅将这些实际新增岗位交给 AI 采后判断。
- 数据库记录显示本批次 V2EX：采集 42，新增 0，更新 11，重复 31；LinuxDo：采集 20，新增 0，更新 0，重复 20。
- 因本批次实际新增 ID 集合为空，AI 采后判断按设计处理 0 个岗位。

## Requirements

- 给出基于代码和数据库的根因结论。
- 区分 worker 候选计数与数据库实际新增计数，避免把 62 条误解为新增记录。
- 将 V2EX、LinuxDo 的完成日志从“入库 N 条”改为“采集候选 N 条”，明确它是进入数据库 upsert 判断的候选数量，不代表实际新增。
- 补充自动化测试，防止完成日志再次使用“入库”描述 `captured`。
- 不改变采集、去重、更新、实际新增记录或 AI 采后判断逻辑。

## Acceptance Criteria

- [x] 能解释 AI 阶段为何收到 0 条。
- [x] 能给出本批次 62 条的新增、更新、重复精确拆分。
- [x] 结论有对应代码路径和数据库记录支持。
- [x] V2EX 与 LinuxDo 完成日志均使用“采集候选 N 条”。
- [x] 相关 worker 测试通过，且测试覆盖新日志语义。

## Out of Scope

- 不修改数据库计数结构、去重规则和 AI 采后判断范围。
- 不在 worker 完成日志中新增数据库实际新增数；实际新增仍以采集记录为准。
