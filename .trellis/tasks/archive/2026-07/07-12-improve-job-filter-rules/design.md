# 继续优化岗位过滤规则设计

## 1. 根因与边界

当前代码已经实现“三段可见文本是个人偏好的唯一事实源”，但本机 `default` profile 保存的是旧版宽松自定义文本，因此新默认模板不会自动覆盖，历史 AI 结果也继续保留。修复分为三个边界：

1. 可见规则：把目标岗位和排除岗位写成可判定、不可补偿的明确条件。
2. 通用协议：只负责真实性门禁、判断顺序、同一岗位证据绑定和结构化输出，不写个人偏好。
3. 本地落地：备份后直接替换本机默认 profile，并通过现有批量链路重算全部历史岗位。

## 2. 新精准规则

### AI 想看的岗位

- 只推荐真实、当前有效、面向候选人的具体招聘或内推岗位。
- 仅接受正式招聘或内推中的以下软件研发方向：Go 后端、Java 后端、AI Agent/LLM 应用开发、AI 工程化研发。正文没有兼职、项目制或短期合作证据时可按常规全职岗位判断，不要求逐字出现“全职”。
- AI 方向允许 Python，但必须用于 Agent、RAG、模型/API 接入、工作流编排或 AI 应用工程；纯模型训练、算法研究、数据分析不属于目标方向。
- 必须明确支持全远程、Remote 或居家办公；没有到岗、混合或附加条件时即可满足，不要求逐字出现“长期、无条件”。试用期、磨合期、表现优秀或后续协商后才可远程仍然排除。
- 多岗位帖子必须能定位到一个独立具体岗位，并确认该岗位自身同时满足目标职责、远程方式及其他全部条件；禁止从不同岗位拼接证据。
- 标题或正文仅出现 AI、Agent、Go、Java、远程等关键词，不构成推荐依据。

### AI 排除条件

任一条有明确原文证据即 `filtered`，不能被其他优点抵消：

1. 要求英语口语/交流、英文会议/汇报、全英面试或持续海外团队英文沟通；仅阅读英文文档不算。
2. 坐班、到岗、线下、混合办公、偶尔远程、远程可协商、试用/磨合后远程、优秀者可远程、优先坐班。
3. 前端、全栈、移动端/客户端、Flutter/H5 等为主要职责。
4. 产品经理/产品运营、开发者关系/Developer Advocate、销售/售前/客服、纯实施交付。
5. 纯推荐算法、算法研究、数据分析/数据科学、模型训练/微调、CV/NLP 研究等非 AI 应用研发岗位。
6. 智能合约或 Web3 为核心主职；不能因同时提到 AI Agent 或 Go 就放行。
7. 兼职、短期外包、项目制合作、个人寻合作/接项目，而不是正式全职招聘。
8. 核心技术方向与 Go、Java、AI Agent/LLM 应用开发、AI 工程化无关。
9. 明确要求全日制本科。
10. 外包、驻场、人力外派、培训/招转培、低代码搭建等。
11. 非招聘内容：开源项目、产品/工具介绍、模拟面试、课程、经验分享、自我介绍、求职/项目合作、资讯聚合帖。

### AI 风险关注点

- 只在事实缺失、矛盾或岗位归属不清时使用。
- 重点核实远程是否无条件长期有效、英语是否只读文档、职责是否为目标研发、多个岗位的条件能否独立归属、招聘是否仍有效。
- 已有排除证据时不得降级为风险或待确认；当前本机不确定策略为 `filtered`。

## 3. Prompt 协议调整

`buildPostCollectionJudgePrompts` 保持个人规则零硬编码，增加通用的“同一岗位证据闭包”：

- 多岗位帖子先选择一个具体岗位作为判断对象。
- 所有正向必选条件必须由该岗位自己的标题、职责和要求共同证明。
- 不得用 A 岗位的远程条件、B 岗位的技术方向和 C 岗位的学历条件拼成推荐结论。
- 按岗位原文的等价语义判断，不因原文没有逐字重复规则中的概括词而误判信息缺失。
- `recommended` 证据至少覆盖招聘真实性、目标职责和所有用户必选条件。
- `filtered` 必须引用命中的可见规则原文和对应岗位原文。

通用来源分类器增加“自我介绍、寻项目合作、接项目、兼职合作”等非招聘意图。产品、算法、Web3 等仍是合法招聘类别，只能由用户可见排除文本处理。

## 4. 重算与通知契约

扩展 `recompute_ai_post_collection_judgement`：

- 新增可选 `notify_telegram` 参数。
- 默认 `false`，避免维护/手动调用意外产生外部副作用。
- 采集完成路径显式传 `true`，保持现有 Telegram 汇总。
- 配置页和职位页手动保存、切换 profile、批量重算显式传 `false`。
- 硬规则命中岗位继续跳过 AI；单岗位失败写入失败状态，其余岗位继续完成。

## 5. 本机数据变更

目标数据库：`~/Library/Application Support/com.administrator.jobpilot/app.db`。

顺序：

1. 使用 SQLite 在线一致性备份生成带时间戳的 `app.db.pre-precise-filter-*.bak`。
2. 读取并记录默认 profile 的旧文本摘要和 `updated_at`。
3. 在单个事务内仅更新三个 AI 文本和 `updated_at`，保留 `aiUncertainStrategy=filtered` 及其他 JSON 字段。
4. 启动当前源码对应的 Tauri 应用并绑定该数据目录，执行无通知批量重算。
5. 查询重算统计、失败项和已知误推荐样本的新 bucket。

回滚时从备份恢复数据库，或将备份中的原 profile JSON 写回后重新执行普通规则与 AI 重算。

## 6. 验证样本

- 应过滤：视频推荐算法、AI 产品经理、全栈/AI Native、优先坐班优秀可远程、个人自我介绍寻合作、智能合约/Web3 主职、兼职/项目合作。
- 多岗位帖：只有可独立定位且完整满足规则的具体岗位才允许通过；条件混杂则过滤。
- 应推荐：正式全职、长期无条件全远程、职责明确的 Go/Java 后端或 Agent/LLM 应用研发。
- 信息不足：当前策略为 `filtered`。

首轮全库重算暴露“逐字证据”过严问题：452 条全部被过滤，包括明确写有“中国境内远程居家办公”的 Go 后端岗位。规则已修正为语义证据，随后真实模型定向烟测中：

- `v2ex:1223546` Go 后端远程岗恢复为 `recommended`。
- `v2ex:1223466` 推荐算法岗、`v2ex:1224418` 条件式远程岗、`v2ex:1223803` 个人寻合作帖保持 `filtered`。

## 7. 兼容性

- 不修改数据库 schema 和 profile JSON 字段名。
- 其他机器和其他自定义 profile 不自动覆盖。
- AI 结构化输出字段保持不变。
- 新通知参数是可选字段，旧调用不会解析失败，但默认改为无外部通知的安全行为。
