# 技术设计

## 根因

1. 前端只展示 `collectionRuns[0]`，多平台任务丢失前序 run。
2. `collection_run.recommended/pending/filtered` 在 worker 结束时写入，早于随后执行的 AI 采后判断，属于旧快照。
3. UI 将 `filtered`（职位最终筛选分桶）误当成“采集规则跳过”，并将 `inserted + updated + duplicate` 标为“写入本地库”，指标名和数据含义不一致。

## 边界与数据流

- 在一次前端自动采集动作开始时生成稳定的 `batch_id`，同一动作内每个平台创建的 `collection_run` 都携带该值。
- `collection_run` 持久化 `batch_id`；历史记录没有值时以自身 run id 作为独立批次兼容。
- 列表查询返回 `batch_id`，前端选择最新 run 所属批次并聚合该批次全部 run。
- AI 采后判断完成后，由后端按批次关联 `collection_run_job` 和岗位当前筛选结果，刷新批次内最终分桶，再由前端重新加载统计。

## 指标契约

- 总搜到：批次内 `captured` 之和。
- 未新增：批次内 `updated + duplicate` 之和；不再冒充“规则跳过”。
- 新入库：批次内 `inserted` 之和，只表示本轮真正新增岗位。
- 通过：批次新增岗位中，采后判断完成后最终处于推荐/通过分桶的数量。

上述口径能解释截图场景：若处理 20 条，其中 11 条新增、9 条已有，则显示“总搜到 20、未新增 9、新入库 11”；通过数在 AI 完成后按这 11 条的最终状态刷新。

## 兼容性与迁移

- SQLite schema 增加可空 `batch_id`，数据库初始化时为旧库执行幂等列迁移。
- 历史 run 缺少 `batch_id` 时仍按单 run 展示，不合并不相关历史采集。
- 不修改 AI 判断、岗位去重、通知和职位库筛选规则。

## 测试边界

- Rust：批次写入、查询、历史空 batch 兼容、批次最终分桶刷新。
- 前端契约/单测：同批次多 run 聚合；新增、更新、重复和通过口径；AI 完成后重新加载。
- 回归：现有 worker/职位审核流程测试、前端构建。

## 回滚

- UI 和批次聚合逻辑可独立回滚；新增的可空列保留不会影响旧版本读取。
- 若批次刷新失败，明确显示错误或旧数据提示，不从日志文本推算数字。
